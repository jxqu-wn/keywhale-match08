日期：2026-10-10。模型：`qwen-track8-text2sql`，服务：`http://192.168.15.119:8000/v1`。

严格比较包含`db`及完整`query`字符串。排版归一化仅合并字符串字面量外的空白、删除末尾分号，不忽略字段前缀、SQL改写或条件差异；这两项都不是执行结果比较。

人工分析将8题分为：2题仅有分号差异、2题等价改写、3题在特定数据下可能不同、1题修改了排他性条件。因此有4题（10%）存在潜在结果差异。**10%是语义分析结论，不是比赛数据库上的实际不一致率或错误率。**

## 抽样与实际流程

从原始`data/raw/subject/QA_train.json`中筛出单源SQLite问题，使用`random.Random(20261010).sample(..., 40)`无放回抽样。原始训练集共5830题，原始知识1800条。样本按抽样顺序为：

```text
4575, 4072, 5938, 3220, 4176, 4488, 4798, 4478, 4602, 4162,
5789, 3804, 3772, 4759, 5023, 3051, 5514, 5286, 4340, 4480,
4968, 5688, 3788, 3885, 4554, 4322, 4358, 3521, 3453, 6015,
3298, 3417, 4217, 4442, 4763, 4344, 5988, 3295, 5030, 4733
```

复用`src/text2query/react/pipeline.py`中的`run_question`，工作流版本5，采用`raw-only`资料模式。每题依次执行：

1. `search_examples`：核对原始训练问答中的同题案例及冲突。
2. `get_schema`：根据实际引用表返回原始DDL和注释。
3. `search_knowledge`：在已确定的数据库范围内按关键词检索原始知识。
4. `check_query`：检查格式、只读限制、库表字段及原始SQLite DDL的`EXPLAIN`编译；随后由同一Qwen模型在独立对话中按题意和证据复核。
5. `finish`：提交最近一次通过检查的查询。复核要求修改时重新检查。

模型实际收到的资料来自`QA_train.json`、`Schema/bird_schemas.txt`及`knowledge.json`；没有使用人工修订问答、人工业务规则或修订知识。不是把整份Schema或knowledge文件塞入请求。

**没有从检索库排除抽中的训练题。审计确认40题各自的原始答案都出现在实际首轮请求中。** 因而本实验衡量当前流程对已知训练题的答案一致性，不能解释为未见题的泛化成绩。原始标注作为比较目标保留，未因为模型修改而替换。

正式运行采用8路并发，每题最多24步，`temperature=0`，关闭思考模式。生成和复核均使用指定模型，无备用模型、无失败题自动重试。

## 6000 tokens限制及请求适配

模型服务的`/v1/models`返回`max_model_len=6000`。未去重尝试留下40题逐题记录，其中4题完成，36题在保留完整工具历史时发生上下文预算超限；例如一个请求输入达到8097 tokens。该尝试的调度被中断，其部分导出指标不作为正式结果，完整逐题汇总见[未去重尝试汇总](../../artifacts/runs/evaluation/sqlite-train40-qwen-track8-react-raw-only-20261010/uncompressed_attempt_summary.json)。

正式运行仅在实验请求包装器中做重复表示去重：

- 同一对象已经逐字段包含原始标注时，删除相同的`raw_annotation`副本。
- 保留完整`raw_schema`，删除其中已经包含的DDL副本、从DDL解析的字段列表及重复注释、外键行。
- 请求中删除来源SHA256、编码元数据；保留来源文件、记录ID和行范围，完整元数据仍保存在磁盘。
- 删除与`candidate`相同的`prediction`副本，压缩JSON分隔空白。

没有截断历史、改写问题和SQL、摘要知识或裁剪原始DDL。上述8097-token请求去重后为4222 tokens。每次请求先经服务`/tokenize`测量，再将输出预算限制为`min(4096, 6000 - 输入tokens - 32)`。正式运行最大输入为5191 tokens，最小输出预算777 tokens，244次响应均以`stop`正常结束，没有长度截断。

审计逐一核对244份实际请求：全部与磁盘原请求按上述规则去重后的消息一致。1197次知识出现、406次问答出现和316次Schema出现均与原始资料相符，1919次来源记录全部指向`data/raw/`；重复历史中的同一资料会多次计数。没有发现非空人工规则或修订资料字段。

因此20%和15%属于**保留原始证据内容、对重复表示去重后的ReAct实验**，不能作为完全不适配6000-token服务时的运行结果。本轮未修改生产ReAct代码。

## 8题差异及原因

| 题号 | 具体差异 | 差异来源 | 对结果的判断 |
|---|---|---|---|
| 4575 | 删除末尾分号。 | 首次生成 | 仅格式差异。 |
| 4478 | `SUBSTR(year,1,4)='2009'`改为`year=2009`。 | 首次生成；依据INTEGER类型及知识1408 | 正常四位年份通常等价；例如DDL允许的异常整数20090会被原式选中、被新式排除。不能据此认定原标注错误。 |
| 3772 | 去掉外层子查询，排序从`COUNT(publisher.id)`改为`COUNT(DISTINCT game_id)`。 | 语义复核要求修改 | 关系记录数变为不同游戏数；有重复发行关系或空game_id时排名可能变化。新写法更直接表达游戏数量，但缺少实际数据，无法判断本库是否受影响。 |
| 5023 | 年份区间从`BETWEEN '1996' AND '2000'`改为`BETWEEN 1996 AND 2000`。 | 首次生成 | 字段为INTEGER，SQLite数值亲和性使这些数字字符串与整数边界比较等价。生成说明中的“避免文本比较歧义”不能证明原式有错。 |
| 3051 | 为`payterms`和`qty`补上`T1.`前缀，调整逗号空格。 | 首次生成 | 这些字段仅来自sales，计算表达式及分母不变，等价。 |
| 4340 | 额外加入`state='AZ'`。 | 首次生成；依据题目及知识139/157 | 题目明确指定亚利桑那州，修改有依据。只有存在其他州同名城市的匹配记录时才改变百分比。 |
| 4554 | 删除末尾分号。 | 首次生成 | 仅格式差异；第20季及演员身份条件仍未落实，见下文。 |
| 6015 | 加入`film_id NOT IN (... WHERE store_id <> 2)`。 | 语义复核要求修改 | 从“2号店有库存”收紧为“只有2号店有库存”，符合“只能”的排他含义。仍保留库存副本导致的重复电影名称。 |

6题在首次提交`check_query`前已与标注不同；3772、6015首次检查与标注完全相同，被独立语义复核指出问题后才修改。这两题各检查2次，其余38题各检查1次。差异主要来自生成模型对类型及条件的改写，以及复核对统计对象和排他语义的判断，不是程序替换了训练答案。

3772的复核解释有一处不准确：原SQL虽然在子查询输出中写了`COUNT(DISTINCT publisher.id)`，**实际排序使用的是`COUNT(publisher.id)`**，并非按恒为1的去重发行商数排序。最终改成不同游戏数可能合理，但复核最初对原SQL排序行为的描述不足以证明原查询错了。

## 构造数据验证与仍存的问题

使用原始SQLite DDL建立内存库，对6道非排版差异题执行8组构造数据。这里的输入是人为构造的反例，不是比赛数据库。

| 题号 / 场景 | 原答案输出 | 模型输出 | 说明 |
|---|---|---|---|
| 4478 / 正常2009年份，含Winner及Nominee | 8.5、7.0 | 8.5、7.0 | 年份改写等价，但两者均包含提名者。 |
| 4478 / 另加入异常年份20090 | 8.5、7.0、6.0 | 8.5、7.0 | 证明前缀筛选与精确年份筛选并非无条件等价。 |
| 3772 / A发行关系3条但均为同一游戏，B发行2个不同游戏 | A | B | 统计粒度会改变发行商排名。 |
| 5023 / 边界年份、数字字符串、NULL及非数字值 | 同一组品牌 | 同一组品牌 | 与INTEGER字段亲和性分析一致。 |
| 3051 / Net 30数量30，其余数量70 | 商店名、30% | 商店名、30% | 字段前缀未改变数量口径。 |
| 4340 / AZ两家商户，其他州同城名另有一家 | 33.33% | 50% | 州筛选改变样本范围。 |
| 6015 / 一部跨店电影、一部2号店独有电影 | 跨店、独有 | 独有 | 排他条件修正有实际作用。 |
| 6015 / 独有电影在2号店有两个库存副本 | 跨店、独有、独有 | 独有、独有 | 最终SQL仍未去重。 |

一致性较高仍可能保留标注缺漏，语义复核接受也不证明正确：

- **4478**问“获得”配音表演奖，知识1416/172明确区分`Winner`与`Nominee`，但原答案及最终SQL均未筛选Winner。复核甚至称不应增加Winner条件，与题意及所检索知识存在张力。
- **4554**问“第20季中哪位演员”，原答案及最终SQL只筛出生信息。此次仅获取Person表，没有验证第20季参演及演员身份；分号差异不影响这个共同缺漏。
- **4340**保留`active='false'`，而原知识139/1342写的是`'False'`。在当前DDL默认文本比较下大小写可能影响匹配；没有实际取值，不能解决原问答与知识的冲突。
- **6015**排他性已补充，但同一电影有多个库存副本时仍返回重复名称；不能把这次修正理解为整个查询已经没有问题。

后续评测应区分文本一致性与执行正确性；若需要测泛化，应从示例检索库排除被测题及同题重复记录。真实执行结果比较还需要相应SQLite数据库。复核值得优先加强的是检查SQL实际排序、关联和过滤行为，以及对原始资料冲突给出明确判断。
