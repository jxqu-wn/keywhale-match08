## ES日均门诊量问题

2128本轮使用 `annual_outpatient > 3650000`。它修复了普通Flash将日均10000直接当作年门诊阈值的问题，但初轮Qwen本来就用了3650000，因此这不是相对初轮的新提升。该换算假设日均=年量/365，而用户尚未确认这一业务公式，Schema裁定仍是待确认。本轮模型自行采用了365天，不能记为业务已确认。

2399改为按 `annual_outpatient` 排序；只有所有医院采用同一正数换算分母时，年量和日均排序才等价。医院等级值由常见训练取值 `'三甲'` 变为 `'三级甲等'`，需要真实索引值确认。此外，本轮设 `size=50`，2128设 `size=100`，若匹配结果更多，会影响返回文档ID范围。2399的床位总和聚合仍针对全部匹配文档，不能据此认为返回ID也完整。

目前没有实际ES索引数据来确认等级取值、结果数量和日均换算公式。

## 原因与后续优先级

ReAct使模型能够查询Schema、知识、示例并检查候选，改善了可执行结构和部分业务口径，但工具检查主要约束表、字段、语法和已编码规则。`page` 与 `revision` 都是合法字段，错误时间字符串也是合法SQL，投票等级的整数转换也可以编译通过，因此“工具通过”不代表“答案正确”。

当前初始领域路由还会影响后续知识和示例的筛选。模型即使查看了另一个数据库，工具内部检索范围仍可能沿用初始路由，形成错误领域内的自洽答案。读取知识这一流程要求，也没有确保模型实际遵守知识；5775即存在读到时间格式后仍错误生成的问题。

后续应优先增加原始知识对应的语义检查，覆盖修订ID、时间格式、统计单位和容器限定；其次检查查询对象与输出列是否符合问题，允许工具发现领域不匹配后重新选择检索范围；再针对跨库候选与歧义公式给出明确裁定。此次结果保持生成时原貌，用于检验本阶段流程效果，上述分析没有回写修改提交查询。

本轮与初轮同时存在模型、训练修订、知识、提示词和流程变化，属于整体流程比较，不能将改善全部归因于ReAct。当前没有本轮官方执行准确率或加权分数；比赛按[官方执行评测标准](../competition/evaluation_standard.md)计算，需平台执行后判断整体好坏。
