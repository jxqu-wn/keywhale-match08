## 逐项分析

### 4976：SQLite保留字表名未加引号

题目：2014年8月交易次数最多的客户全名是什么？

判定：结构/语法问题（确定）。

```sql
SELECT T1.First, T1.Last FROM beer_factory.customers AS T1 INNER JOIN beer_factory.transaction AS T2 ON T1.CustomerID = T2.CustomerID WHERE T2.TransactionDate LIKE '2014-08%' GROUP BY T1.CustomerID ORDER BY COUNT(*) DESC LIMIT 1
```

证据：原始DDL为CREATE TABLE "transaction"；提交使用beer_factory.transaction。EXPLAIN报near "transaction": syntax error。

原因推断：模型生成了正确的交易关联方向，却漏掉标识符引号；基础校验只识别表名，不调用SQLite编译。

改进方向：将物理表写为beer_factory."transaction"，并对SQLite结果做原始DDL上的编译检查。

历史检索：示例题号 `5010, 5228, 5003, 6092, 5056`；知识ID `317, 309, 602, 1202, 323, 330, 322, 385, 226, 337`。

### 5029：UNION分支排序不合法，且容器字段属于另一张表

题目：找出单位利润最高和最低的根汁啤酒，并列出这些根汁啤酒销售的容器类型。

判定：结构/语法问题（确定）。

```sql
SELECT T2.ContainerType FROM beer_factory.rootbeer AS T1 INNER JOIN beer_factory.rootbeerbrand AS T2 ON T1.BrandID = T2.BrandID WHERE T2.BrandID IN (SELECT BrandID FROM beer_factory.rootbeerbrand ORDER BY CurrentRetailPrice - WholesaleCost DESC LIMIT 1 UNION SELECT BrandID FROM beer_factory.rootbeerbrand ORDER BY CurrentRetailPrice - WholesaleCost ASC LIMIT 1)
```

证据：两个UNION分支直接带ORDER BY/LIMIT，SQLite编译失败；只修正集合语法后，仍报no such column: T2.ContainerType。ContainerType在rootbeer即T1中。

原因推断：检索示例4970提供最低利润排序，5071提供容器关联。模型把两个Top1查询直接拼接，并在重新命名别名时绑定错列。

改进方向：分别包装最高/最低利润子查询，或用MAX/MIN利润筛选；输出T1.ContainerType。修复后重新编译，不能只消除第一条错误。

历史检索：示例题号 `4970, 5071, 5020, 4998, 5052`；知识ID `228, 463, 473, 472, 434, 438, 226, 460, 222, 1645`。

### 1825：MySQL查询使用FULL OUTER JOIN

题目：统计2024与2025中每个院系的课程数量，按课程数降序取前15，输出院系编号、两年课程数。

判定：结构/语法问题（确定）。

```sql
WITH c2024 AS (SELECT department_id, COUNT(*) AS course_cnt_2024 FROM education_2024.course GROUP BY department_id), c2025 AS (SELECT department_id, COUNT(*) AS course_cnt_2025 FROM education_2025.course GROUP BY department_id) SELECT COALESCE(c2024.department_id, c2025.department_id) AS department_id, COALESCE(c2024.course_cnt_2024, 0) AS course_cnt_2024, COALESCE(c2025.course_cnt_2025, 0) AS course_cnt_2025 FROM c2024 FULL OUTER JOIN c2025 ON c2024.department_id = c2025.department_id ORDER BY (COALESCE(c2024.course_cnt_2024, 0) + COALESCE(c2025.course_cnt_2025, 0)) DESC, department_id ASC LIMIT 15;
```

证据：db为MYSQL，SQL对2024/2025课程汇总做FULL OUTER JOIN。MySQL JOIN语法支持LEFT/RIGHT，不支持该写法。这里是方言核对，未连接MySQL执行。

原因推断：模型需要保留两个年份中单边存在的院系，选择了其他SQL方言的全外连接；校验未按目标方言解析。

改进方向：先UNION两年院系键，再LEFT JOIN两个汇总；跨年院系身份应按已确定的业务编号对齐。

历史检索：示例题号 `1661, 2000, 1953, 2027, 1831`；知识ID `325, 1580, 335, 36, 114, 274, 1353, 1357, 345, 1450`。

判定：语义问题（题意、Schema或反例支持）。

```sql
SELECT T1.coachID, T3.name FROM hockey.Coaches AS T1 INNER JOIN hockey.Teams AS T3 ON T1.tmID = T3.tmID AND T1.year = T3.year WHERE T1.year BETWEEN 1970 AND 1980 GROUP BY T1.coachID ORDER BY MAX(T1.year) - MIN(T1.year) DESC LIMIT 1
```

## 原因归纳及改进顺序

1. **先补执行前检查。** SQLite原始DDL编译可直接挡住3条硬错误；MySQL必须做目标方言约束，ES要递归检查子句并绑定mapping字段。旧检查只保证JSON/根结构/表名/只读词法，所以这些输出不会触发修复轮次。
2. **纠正实体粒度，再做统计。** 商家/球员/游戏/角色问题反复出现JOIN后的COUNT错误。按实体主键去重、按业务粒度预聚合、用EXISTS表达存在性，不能把DISTINCT机械地加到所有查询。
3. **清洗错误训练SQL和矛盾知识。** 4123沿用4298的错误分母是强证据；4207的知识同时包含裸减法与AM/PM字符串定义。当前清洗主要解决结构、重复与跨年冲突，没有保证所有非冲突样本的业务正确性。仅增加召回量或embedding不能修复错误知识。
4. **先确定数据源，再补必须的领域事实。** 对4682确保年龄/国家问题ID及值召回，对3576确保单位及公式，对649/846确保区划行及层级。字典、知识和示例都要标记来源并按目标库约束；字段相同不代表枚举相同。需要从计算公式递归召回依赖，例如PB还依赖BPS定义。
5. **把时间和地理常量交给确定规则。** 检查日期字符串样例、使用半开区间、转换AM/PM、用程序转度分坐标。题目提供知识仍有生成落笔错误，不能只靠检索。
6. **以新口径生成新版本后再评测。** 旧教育输出没有当前跨年合并规则；本次直接调用当前年份识别器，1737日期20240101确实被识别为explicit_year/2024，仍需修正日期值与数据库年份的区分。现有船舶来源裁定只覆盖油轮，未补货船。最新修正规则只对完整题目精确匹配或RAG示例生效，不代表旧400条已经修复。

## 审计中避免的误判

- 不把“整数除法”一律当错误：3202的Stars > Forks*1/3，3348的整数计数 > 均值，在当前整数严格大于比较中截断可能不改变真值，不能仅凭运算符判错。
- 不以通用财务定义覆盖本地知识：418的每股净资产按知识1624、537的波动率按知识1640等，应首先尊重赛题显式口径。
- 不把解析后catalog列缺失当真实DDL缺列：language_corpus首行列wid等在原始DDL中存在；Disney带空格/连字符标识符也有元数据提取缺陷。编译使用完整DDL，所以未将这些解析问题误算成提交错误。元数据提取本身仍可影响召回质量。
- 题目“统计值”、代理键与实际年份、自然语言“瓶”、国家路由没有唯一确证时列为条件性风险。
- 不把后来增加的跨年合并、优先2025规则回推成旧提交当时的确定错误，也不猜83条平台失败题的具体ID。
